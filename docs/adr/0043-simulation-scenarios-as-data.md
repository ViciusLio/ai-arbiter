# 0043: Simulation scenarios are data files, loaded into a tenant of their own

## Context and Problem Statement

The brief asks for a sandbox with example scenarios, invented systems that have problems
and invented systems that have none, for demonstrations and training. The scenarios are
also the first labelled set on which the scan rules can be measured (I-13, I-27): a
scenario that says what should be found lets a test say whether it was.

## Considered Options

- **1.** YAML files: declarations, synthetic traffic and the outcomes expected, loaded
  by `arbiter demo run NAME` into a dedicated tenant; tests compare the outcomes.
- **2.** Scenarios generated by Python code.
- **3.** A demonstration database, already populated, shipped as a file.

## Decision Outcome

Chosen option: **1**.

- A scenario is one YAML file shipped with the package: a description, the systems to
  declare, traffic described as counts per system (never text), reviews to record, and
  the expected indicative tier and findings of each system.
- `arbiter demo list` shows the scenarios; `arbiter demo run NAME` loads one into the
  tenant `demo`, classifies, scans and prints what was found next to what was expected.
  It never writes to another tenant, and running it again replaces nothing: it is
  idempotent like `systems apply`.
- The traffic of a scenario is written as interactions with the source `simulation`,
  so that it can be told apart from real traffic everywhere.
- Every scenario is run by the test suite, which fails when an expected outcome is not
  produced or an unexpected finding appears.
- Scenarios are data, with no code, like rule packs (ADR-0012).

### Consequences

- Good: a person who does not program can read and write a scenario.
- Good: a change to a rule that alters an outcome fails a test and has to be explained.
- Bad: a scenario states traffic as counts, so it cannot exercise the gateway itself;
  that remains the job of the gateway tests.

## Pros and Cons of the Options

| Criterion | 1. YAML files | 2. Python code | 3. Populated database |
|---|---|---|---|
| Complexity | Medium: a schema and a loader | Medium | Low |
| Azure cost | None | None | None |
| Scalability | Not relevant | Not relevant | Not relevant |
| Security | Invented data in a tenant of its own | As 1 | A file whose content is opaque |
| Compliance / privacy | No real data; marked as simulation | As 1 | As 1 |
| Maintainability | Readable; checked by tests | Readable by developers only | Breaks at every migration |
| Lock-in | None | None | None |
