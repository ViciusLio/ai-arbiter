# 0009 — Scope v0.1 as one complete vertical slice

> Status note: the scope table was presented in Phase 0. The project owner decided D1–D7
> and the Phase 1 ADRs and asked to proceed, but the scope line in both decision notes
> was left unfilled. It stays `proposed` until confirmed, including the amendments below.
> Phase 2 does not depend on it.

## Context and Problem Statement

Fifteen modules built to the same depth would leave none of them demonstrable. v0.1 needs
a boundary that produces a working end-to-end path.

## Considered Options

- **A.** Vertical slice: request → policy → routing → metering → audit → inventory →
  classification → finding → digest, each module at reduced depth.
- **B.** Horizontal: finish the gateway completely, then start compliance.

## Decision Outcome

Proposed option: **A**.

### In v0.1

| Module | Content |
|---|---|
| core | Config, plugin registry, domain model, tenant context, PostgreSQL/SQLite persistence, in-process event bus with outbox, audit log, rule engine, redaction, i18n, OpenTelemetry bootstrap |
| llm_router | `/v1/chat/completions` with SSE streaming, `/v1/models`; Azure OpenAI, OpenAI-compatible and mock adapters; routing by priority, cost and risk-class constraints; fallback and retry |
| finops | Metering per tenant/team/project/user/AI system; versioned price catalogue; soft and hard budgets; usage API and Markdown report |
| policy | Pre- and post-call evaluation; PII detection and redaction; model and region allowlists per risk class; budget enforcement |
| audit | Append-only hash chain per tenant; verify command; JSONL export |
| identity | Tenants, teams, projects, hashed API keys, three roles |
| inventory | Declared systems (YAML/API/CLI) with AI Act role; discovery from traffic; undeclared-use detection |
| classifier | Versioned rule pack; outcomes: out of scope, prohibited, high-risk (Art. 6, Annex III, Art. 6(3) derogation), transparency (Art. 50), minimal; rationale, articles, application dates |
| scanner | 10–15 high-precision rules over configuration, inventory and traffic metadata |
| findings | Full model, state machine with human review, suppressions |
| daily_digest | Markdown and HTML, CLI command, optional SMTP delivery |
| local_agent | Static, consented, read-only discovery of MCP configurations and known AI tools |
| simulation | Four scenarios used as demo data, test fixtures and rule benchmark |
| reporting | System and audit reports in Markdown and HTML |

### Out of v0.1

| Item | Target |
|---|---|
| A2A, MCP registry and proxy | v0.2 (Phase 5), on the explicit roadmap |
| LiteLLM push endpoint, Azure APIM ingestion | v0.2 |
| Azure deployment, Entra ID, signed audit checkpoints, PostgreSQL row-level security | v0.3 (Phase 6) |
| Latency-based routing, embeddings, semantic cache, optimisation recommendations | v0.2 or later |
| OPA adapter, external content-moderation classifiers | After v0.1, by ADR |
| PDF export, web dashboard, dataset analysis, network-flow capture | Not scheduled |

### Acceptance criterion

From a clean clone, `docker compose up` and one demo command show in under five minutes:
a request blocked by policy, a request routed by cost, cost attributed to a project, the
audit chain verified, the four simulated systems classified with articles and dates, and
a digest listing the findings in English and Italian.

### Consequences

- Good: every phase ends with something runnable.
- Bad: each module is thinner than the brief describes; the gaps are listed above and in
  the README.
