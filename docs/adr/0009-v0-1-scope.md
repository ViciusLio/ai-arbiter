# 0009 — Scope v0.1 as one vertical slice, split into a core and deferrable components

## Context and Problem Statement

Fifteen modules built to the same depth would leave none of them demonstrable. v0.1 needs
a boundary that produces a working end-to-end path, and a rule for what gives way if
the work takes longer than expected.

## Considered Options

- **A.** Vertical slice: request → policy → routing → metering → audit → inventory →
  classification → finding → digest, each module at reduced depth.
- **B.** Horizontal: finish the gateway completely, then start compliance.

## Decision Outcome

Chosen option: **A**, confirmed by the project owner with one change: inside v0.1 a
**core** that cannot be given up is distinguished from **components that may slip to a
v0.1.x release** without compromising the demo.

The owner named the core (proxy with FinOps and audit, classifier, findings, digest, CLI)
and gave examples of what may slip (routing by risk class, LiteLLM import, simulated
scenarios). The tables below apply that rule to every item of the scope. Items the owner
did not name are placed by the same test: *does the demo below still work without it?*
Modules the core cannot run without (identity for the proxy, inventory for the
classifier, a first scanner rule set for findings) are part of the core.

### Core — v0.1.0

`0.1.0` is not released until all of this works.

| Module | Content |
|---|---|
| core | Configuration, plugin registry, persistence on SQLite and PostgreSQL, event outbox (done in Phase 2); rule engine; audit log with per-tenant hash chain, verification and JSONL export; EN and IT message catalogues |
| identity | Tenants, teams, projects, hashed API keys, three roles |
| llm_router | `/v1/chat/completions` with SSE streaming, `/v1/models`; mock, OpenAI-compatible and Azure OpenAI adapters; routing by priority and by cost; fallback and retry |
| finops | Metering per tenant, team, project, user and AI system; versioned price catalogue; soft and hard budgets; usage API and Markdown report |
| policy | Pre-call evaluation: model allowlist, budget enforcement, PII detection and redaction on the prompt with the built-in EU and Italian detectors |
| inventory | Systems declared through YAML, API or CLI, with their AI Act roles |
| classifier | Versioned rule pack verified against EUR-Lex; outcomes: out of scope, prohibited, high-risk (Art. 6, Annex III, Art. 6(3) derogation), transparency (Art. 50), minimal; rationale, articles, application dates |
| scanner | A first set of high-precision rules over the inventory and gateway traffic metadata, enough to produce real findings |
| findings | Full model, state machine with human review through CLI and API, suppressions |
| daily_digest | Markdown and HTML, in English and Italian, produced by a CLI command |
| CLI and API | `arbiter` commands for all of the above; curated OpenAPI documentation (ADR-0006) |

### Deferrable — v0.1.x

Planned for v0.1. Each may be released after `0.1.0`, in a v0.1.x release, if it would
otherwise delay the core.

| Component | Note |
|---|---|
| Routing constraints by risk class (allowed models and regions per class) | Named by the owner. The bridge from classification to routing; the data it needs exists in the core |
| LiteLLM file importer and generic JSONL importer | Named by the owner. The ingestion port (ADR-0019) is defined with them |
| Simulation scenarios | Named by the owner. Until they exist, the demo uses example system declarations kept in `examples/` |
| Discovery of systems from traffic; detection of undeclared use | Needs the gateway and the inventory, both in the core |
| Post-call policy evaluation | Detection on completions; enforcement only for non-streaming responses |
| Remaining scanner rules, up to the planned 10–15 | |
| System and audit reports (Markdown and HTML) | The digest is in the core; reports reuse its rendering |
| Digest delivery by SMTP | The digest files are in the core |
| Local agent: static, consented, read-only discovery | |
| Opt-in store of redacted content with retention (ADR-0018) | Metadata-only persistence is in the core |
| External anchoring of the audit chain head (ADR-0017) | Must exist before Phase 6 in any case |

### Acceptance criterion for 0.1.0

From a clean clone, with no container runtime, the documented quickstart shows in under
five minutes:

1. a request proxied to the mock provider, metered, with its cost attributed to a project;
2. a request denied by policy, with the decision and its reasons;
3. the audit chain verified;
4. systems declared from the example files classified with articles and application dates;
5. findings listed, and one of them reviewed;
6. the digest of the above, in English and in Italian.

### Consequences

- Good: every phase ends with something runnable, and it is decided in advance what
  gives way under time pressure.
- Good: the core demo depends on nothing deferrable.
- Bad: with risk-class routing deferrable, `0.1.0` may ship without the most distinctive
  link between the two halves of the product. It is the first deferrable item to
  implement.
- Bad: each module is thinner than the brief describes; the gaps are listed above and in
  the README.
- Follow-up: the phase summaries of Phases 3 and 4 report, item by item, what landed in
  `0.1.0` and what moved to v0.1.x.
